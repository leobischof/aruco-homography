# Stufe 2: Der C++-Rechenkern

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Ziel:** `app/vision/` (~1 020 Zeilen) als C++-Bibliothek in `core/`, mit
`pybind11`-Bindung — und die **vorhandene Python-Testsuite läuft dagegen**, unverändert.

**Architektur:** Eine C++-Bibliothek, drei Bauziele (heute nur MSVC; NDK und Emscripten
in Stufe 4). Python bleibt als **geprüfte Referenz** bestehen und wird nicht ersetzt,
sondern *danebengestellt*: eine Umgebungsvariable entscheidet, welche Implementierung
die Suite fährt.

**Tech Stack:** C++17, CMake, OpenCV 5.0.0 (Windows-SDK), pybind11, MSVC 14.50.

## Global Constraints

- **Der Kern fasst `cv::imread`/`imwrite`/`imencode`/`imdecode` NICHT an.** Im
  WASM-Bau ist `imgcodecs` abgeschaltet (Stufe 0, nachgemessen). Der Kern nimmt einen
  **rohen Pixelpuffer plus Maße** und gibt einen solchen zurück. Kodieren gehört auf
  jedes Ziel einzeln. Heute ist der Python-Messkern schon sauber — `cv2.imread` steht
  nur in `pipeline.py` und `session.py`, beides Vorschaudateien. **Das muss so bleiben.**
- **Konstanten kommen aus `shared/constants.json`** (Invariante 4). Der C++-Kern
  bekommt einen **erzeugten** Header, keine abgetippten Zahlen. Erzeugt wird er beim
  Bau; die erzeugte Datei ist **nicht** eingecheckt.
- **`shared/fixtures/` ist der Vertrag.** `core/tests/` prüft gegen **dieselben**
  Dateien und **dieselben** Toleranzen wie `tests/test_conformance.py`.
- **Die Python-Suite bleibt grün.** Ausgangslage `develop`: **174 Tests**.
- **Millimeter sind das Produkt.** Ein C++-Kern, der übersetzt, aber um einen
  Zehntelmillimeter danebenliegt, ist schlimmer als keiner — er sieht richtig aus.
- Git: committen ohne Rückfrage; **PRs zielen auf `develop`**, niemals auf `master`.
  Autor `Leo Bischof <leo@bischof-snowboards.com>`.

## Wie die Übereinstimmung belegt wird

**Es gibt keine zweite Testsuite.** Die vorhandene läuft gegen beide Kerne.

```
ARUCO_CORE=python   (Vorgabe)   ->  app/vision/*.py          wie bisher
ARUCO_CORE=cpp                  ->  core/ ueber pybind11
```

`app/vision/backend.py` wählt beim Import. Jedes Modul in `app/vision/`, das portiert
ist, holt seine Implementierung von dort statt sie selbst zu definieren. Die Tests
merken davon **nichts** — sie rufen weiter `detect_markers(...)`.

`.\dev.ps1 run-tests` fährt Python, `.\dev.ps1 run-tests-cpp` fährt C++. **Beide grün
zu haben ist das Abnahmekriterium der Stufe.**

Warum so und nicht mit einer zweiten Suite: zwei Suiten driften genauso wie zwei
Implementierungen, nur unbemerkt. Eine Suite, zwei Kerne, ein Ergebnis.

## `core/` — Aufbau

```
core/
├─ CMakeLists.txt
├─ include/aruco/
│  ├─ types.hpp          # ImageView, Marker, Solution — die Grenze
│  ├─ detect.hpp
│  ├─ solve.hpp
│  ├─ geometry.hpp
│  └─ constants.hpp.in   # Vorlage; constants.hpp wird erzeugt
├─ src/
│  ├─ detect.cpp
│  ├─ solve.cpp
│  └─ geometry.cpp
├─ bindings/
│  └─ python.cpp         # pybind11 -> Modul `aruco_core`
├─ tests/
│  └─ conformance.cpp    # gegen shared/fixtures/, wie tests/test_conformance.py
└─ tools/
   └─ gen_constants.py   # shared/constants.json -> constants.hpp
```

**`types.hpp` ist die wichtigste Datei.** Sie ist die Grenze, an der später Android und
WASM andocken. Sie darf **nichts** aus `imgcodecs` kennen:

```cpp
namespace aruco {

// Ein Bild, das dem Kern NICHT gehoert. Wer es besitzt, weiss der Aufrufer:
// im Browser der Canvas, in Python ein numpy-Array, auf Android ein Bitmap.
// Der Kern liest nur -- deshalb const, deshalb kein Dekodieren, kein Laden.
struct ImageView {
    const uint8_t* data;
    int width;
    int height;
    int stride;      // Bytes je Zeile, nicht Pixel
    int channels;    // 1 = grau, 3 = BGR
};

struct Marker {
    int id;
    double corners[4][2];   // TL, TR, BR, BL — dieselbe Reihenfolge wie cv2.aruco
};

}  // namespace aruco
```

### Warum `detect` zuerst und nicht `geometry`

Weil `detect` das einzige Modul ist, an dem der Umzug **scheitern** kann. Alles andere
ist Numerik, die sich nachrechnen lässt; die Markererkennung mit Subpixel ist die
Messtechnik selbst. Wenn sie in C++ dieselben Ecken liefert wie in Python, ist die
Stufe im Wesentlichen bewiesen — und wenn nicht, hat man drei Tage investiert statt
drei Wochen.

## Aufgaben 2–5 (Reihenfolge, Begründung knapp)

Jede folgt demselben Muster: portieren, Bindung, `ARUCO_CORE=cpp` grün, commit, PR.

| # | Modul | Zeilen | warum an dieser Stelle |
|---|---|---:|---|
| 2 | `solve` | 248 | die zweite Hälfte der Messung; `least_squares` → `cv::LevMarq` |
| 3 | `geometry` + `rectify` | 178 | Numerik, gut nachrechenbar, wird von 2 gebraucht |
| 4 | `camera` + `extent` + `thickness` + `contour` | 313 | Nebenrechnungen, kein Messrisiko |
| 5 | `enhance` | 199 | ausdrücklich **kosmetisch** (Invariante 6) — zuletzt, weil ein Fehler hier keine Millimeter verschiebt |

**Zu Aufgabe 2, `least_squares`:** Python nutzt `method="trf"` mit
`xtol=ftol=gtol=1e-14`. Der Gegenpart in C++ ist Levenberg-Marquardt, nicht
Trust-Region-Reflective. Die Ergebnisse **müssen** trotzdem innerhalb der Toleranz
zusammenfallen — beide minimieren denselben Reprojektionsfehler ohne Schranken. Tun sie
es nicht, ist das der interessanteste Befund der ganzen Stufe und gehört ins Protokoll,
nicht in eine gelockerte Toleranz.

**Er heißt aber nicht `cv::LMSolver`.** Nachgemessen am SDK dieses Projekts (Aufgabe 1,
2026-09-08): `grep -ri lmsolver` über die gesamten OpenCV-5.0.0-Kopfdateien findet
**nichts**. Die Klasse hieß so in OpenCV 4 und lag in `calib3d`. In 5.0.0 heißt sie
**`cv::LevMarq`**, ist öffentlich (`CV_EXPORTS`) und steht in
`opencv2/geometry/3d.hpp` — also im Modul **`geometry`**, nicht in `calib`. Sie nimmt
einen Callback und eine `Settings`-Struktur.

Dasselbe Modul ist schon in Aufgabe 1 nötig geworden: **`cv::contourArea` ist in
OpenCV 5 von `imgproc` nach `geometry` gewandert.** `geometry` gehört damit auf die
Liste der Module, die der WASM-Bau von Stufe 4 mitbringen muss — beide Hälften der
Messung hängen daran.
